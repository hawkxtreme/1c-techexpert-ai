# 1C TechExpert AI

## Repository and verification

- The product uses the user's AI harness. The local tools compute, verify and retain evidence. The harness interprets it. Keep skills reusable and use SC-01 as the first regression case. Read the relevant skill and executable contract for the task.
- The approved specification is in the user's Pages. The Git checkout contains its numbered requirements in `docs/requirements.md` and the Windows Dev procedure in `docs/dev-windows.md`. README covers the available workflow. The command registry and actual verification define supported implementations.
- Runtime uses the Python 3.11+ standard library. After core changes run `python -m unittest discover -s tests -v` and `python techexpert.py demo`. Keep skill commands executable. After editing inventoried content run `python scripts/generate_bundle_manifest.py --write`, then run it without flags.
- The demo is synthetic `normalized-events-v1`. Confirm native compatibility using native evidence for the exact platform and environment. Check plugin discovery in a clean extracted package under an owned client profile. Protocol tests establish the tested protocol only. Model use, token results and human acceptance require their own evidence.
- Keep plugin identity, launch command and version consistent across metadata and the release inventory. Stage a checked package at a separate path, verify saved-state capabilities and require an explicit maintenance window for a selected managed upgrade. Preserve evidence and a compatible rollback. Repository work does not authorize publication, production changes or a new model provider.

## Profiles, sources and setup

- Inputs stay at separate selected paths. Keep logs, source snapshots, credentials, state and draft incident materials outside Git. Preserve evidence until the user selects removal or a retention policy. `state-location` changes a revisioned default for future executors. An already bound MCP process keeps its selected state.
- Discovery and readiness are passive. Source checks, RAS queries, collection, imports and exports are explicit actions. GUI GET/save must not connect, start data collection, change platform configuration or grant access. Full MCP `techexpert_init` returns a verified, short-lived, process-owned loopback URL only on explicit open. Reuse its key in the same process and check the linked revision after saving.
- Require the exact displayed profile revision and the expected investigation revision for binding. Preserve an unrelated active environment when editing a case profile. Keep historical profile snapshots and source bindings. Store the canonical graph with mode, address origins, shared connections and per-base mappings. Resolving a legacy adapter view is read-only. Prevent silent schema downgrade and invalidate obsolete identity or rights claims after connection edits.
- RAC and database adapters use fixed read-only catalogues. Keep SQL credentials in the operator's environment or approved references. Distinguish access denial, lack of retained history and an empty visible result. OS plans default to 300 seconds and a one-second interval. Collection requires an explicit bounded invocation. A local stop can leave remote termination unknown.
- Source code is accepted as a directory or Git revision. The supported Designer export uses a private copy of the selected Windows/file/8.3.27.1989 IB, fixed arguments, explicit admission and owned process cleanup. Preserve the original configuration and access settings. An editable main configuration does not establish correspondence to runtime, extensions or an earlier incident.
- Configuration preparation for `logcfg.xml` is an offline proposal. Retain original bytes, exact target, scoped additions and rollback checks. XML retention settings do not enforce a collection deadline or byte quota. Remote journal plans are separate from connection, bounded capture and parsing of retained bytes. Preserve the selected public trust material, keep private keys by reference and retain incomplete work.

## Evidence and investigation

- Pin immutable revisions, exact input bytes and the evidence supporting each assertion. Replay from retained verified snapshots. Use explicit source and time scopes. Preserve queue, execution, observed calls, effect and root cause as distinct fields. A CALL/SCALL, an identifier or a matching payload does not establish the whole job.
- Validate each supported reader profile and bounded observation. Preserve quote-aware native TJ framing and raw incomplete tails. Separate byte/coverage observations from timestamps, clock alignment, identity and collection completeness. Two matching reads can support a bounded snapshot. They do not establish atomicity or prove an absence in an unobserved interval. A catalogue preview must bind to the actual selected bytes before import.
- Associate source passports with their own saved profile revisions. Distinguish configured, reported and observed identity. Attach known links and label only the conclusions affected by uncertainty. Keep old assessments available, mark their changed basis and require a new assessment for a new basis. A knowledge card, digest or structurally valid report does not prove a cause.
- For periodic incidents prepare sources and a bounded plan, save `awaiting_occurrence` and end the current stage. Resume in the same harness chat when the user or an external monitor reports an episode. Distinguish event reports, evidence and actual collector execution.
- For a fix, pin the relevant evidence and compare the agreed operation, workload, versions, measured outcomes and coverage. Retain failures, ambiguous results and exclusions. Keep application of the fix, measured effect, correctness, goals and recurrence separate. Apply the full controlled comparison criteria where claimed.

## Managed operations and retention

- Use finite operation and program catalogues, persistent keys, kernel-held writer locks, process lifetime identities and sealed output. After uncertainty read status or repeat the same key. Permit only the owned worker. Separate preparing, starting, running, cancellation requested and verified stop. Retain incomplete private work, and promote verified products without overwriting a central ID.
- Bound admission, execution, replay, finalization and the first output in the managed controller. Preserve prepared results and inspect separate invocation receipts. Windows Job accounting includes nested local workers. Linux inherits the smaller address-space bound per process. Keep an owned Linux leader until group cleanup is verified. Use atomic Job assignment on Windows. Unknown visibility blocks reconciliation. Disk monitoring and transport are bounded on their stated axes. Legacy routes, the harness and remote hosts retain their own limits.
- Validate the whole CodeMode AST and scope before any call. Use the finite supported APIs. Retain journals, propagate cancellation and verify child outputs on replay. Keep host objects and general execution out of programs. MCP discovery is passive. Preserve per-request metadata and verify sealed output before streaming. Cancel only the owned RPC and retain separate payload, wrapper and timing receipts.
- Treat indexes as disposable private accelerators. Preview removals against exact scope, revision, dependencies, policy and identities. Require verified ownership and the selected removal; distinguish missing receipts and unknown outcomes from successful deletion. Export packages pin the exact revision, content scope and member hashes.

## Disclosure and knowledge

- Scope typed harness views to the current policy, exact investigation revision and verified attachments. Apply limits and allowlists before preparation, on replay and before delivery. Keep raw input private. Record prepared disclosure separately from delivery. Source excerpts require the approved bytes and verifiable evidence coordinates. Follow the protected tool boundary and preserve current revocation checks.
- Ship independently authored knowledge cards with a versioned index, applicability, status and URL references. ITS originals, credentials and the private corpus stay outside Git. Distinguish technical withdrawal, conflicts, dependencies and link availability. Verify saved knowledge-use before reusing old recommendations. Never rewrite old assessments or include raw private provenance in an incident export.
- Review the exact sanitized incident preview with the user. Only explicit approval of that preview and its destination permits a GitHub submission. Read the issue back before recording its receipt. Held-out SC-01 evaluation uses a separate labelled projection and sealed stages. Only the approved evidence reaches the participant at each stage.
