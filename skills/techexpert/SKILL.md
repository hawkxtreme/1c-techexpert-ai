# 1C TechExpert AI

Работай с проблемой пользователя и его окружением. Сохраняй уже известные сведения из чата; выбирай инструменты по требуемым доказательствам и их фактическим возможностям. Текущий harness предоставляет ИИ, диалог и разрешения. Исходники, журналы и серверы остаются по своим адресам.

Корень пакета находится на два уровня выше skills/techexpert/. Используй `techexpert.py` из этого корня или точный путь к пакету, указанный для текущей задачи.

## Чтение готовых материалов

При известных ID расследования, ревизии, метках и виде начни с `context-read ID KIND --revision N --attachment LABEL` или `techexpert_context_read`. Для нескольких сводок одного вида повтори `--attachment` в одной команде или передай массив `attachments` в MCP. Ссылки на каждую сводку находятся в `data.views[].disclosure`.

Инструмент проверяет текущую политику. По запросу согласования покажи план для нужной категории. При `context_state_access_denied` проверь доступ к служебной папке и её родительским каталогам из текущего harness. Повтори чтение после подтверждения доступа. Открой [справку о чтении](references/mcp.md#выдача-сохранённых-данных-модели), если не хватает параметра. Скрытый фрагмент запрашивай через отдельный просмотр, когда от него зависит вывод.

После чтения верни вывод в запрошенном формате со ссылками из результатов. Когда нужен ответ в чате, отдай итог в сообщении. Файл ответа сохраняй, когда задача задаёт этот способ выдачи. Обновляй расследование при сообщении о новом событии, изменении материалов или переходе к следующему этапу. При сохранении укажи ожидаемую ревизию.

## Настройка и расследование

1. Восстанови известное расследование и профиль. Новую задачу сохрани через `techexpert_investigation_task` или `investigation-task REQUEST.json`. Передай исходную формулировку пользователя в `text` и известные сведения о случае. При уточнении сохрани новое сообщение с текущими `investigation_id` и `expected_revision` в `context`. Передай только изменившиеся сведения. После потери ответа повтори запрос с тем же `operation_key`. Шаблон помогает выбрать проверки, а «обычно пять минут» остаётся пользовательской оценкой.
2. Если нужны источники, открой мастер из того же чата через `techexpert_init` или CLI `init`. [Открытие и возврат после сохранения](references/first-run.md). GUI помогает связать базы и общие ресурсы и указать независимые источники. Список стартера читается только явно; starter-inspect без пути читает стандартный список текущего пользователя, не обходит связанные файлы и не открывает базы. В GUI похожие записи сопоставляются по параметрам, объединяются только по выбору пользователя; ID стартера не является UUID ИБ. RAS читается отдельным действием; свойства выбранной ИБ могут предложить SQL-настройки без подключения к СУБД и без замены существующего источника. После сохранения прочитай profile --resolved и продолжи задачу; исходный профиль с общими ресурсами сохраняй в его версии, не подменяй плоским представлением. Сохранение конфигурации не запускает сбор.
Для ТЖ и ЖР из сохранённого профиля начни с `source.check` и `profile_journal` через `context-intake` или `techexpert_context_intake`. Используй границы сообщения о событии либо сохранённого эпизода. Если для ТЖ уже дали копию `logcfg.xml`, проверь правило перед уточнением формата. Спроси только недостающие сведения. Снимок импорта связывается с текущим расследованием. Для отдельно предоставленного каталога или ZIP сначала используй `input.inspect`. [Команды](references/mcp.md#первичный-приём-тж-и-жр)

В шаге источников **«Найти ТЖ файловых баз»** предлагает каталоги из `logcfg.xml` открытого клиента 1С 8.3.27.1989 на Windows. **«Найти ЖР файловых баз»** предлагает стандартный ЖР. Пользователь выбирает адрес. Для проверки локальных файлов используй отдельное действие в GUI или `profile-files`. Учитывай различие между адресом из настроек, прочитанным заголовком и покрытием инцидента.
3. Сопоставь доступные материалы с задачей, периодом и ограничениями. Для файловой базы учитывай неприменимость SQL/RAC. Недоступный источник не останавливает независимые проверки.
Перед выводом, зависящим от связи нескольких источников, сохрани source_bindings/source_links в расследовании и прочитай investigation.sources для его точной ревизии. Агент подготавливает эти данные из известного профиля и уже полученных артефактов; ручного паспорта инфраструктуры от пользователя не требуй. Уточняй только связь, от которой зависит конкретный вывод. [Контракт принадлежности](references/investigation-state.md) задаёт поля и границы подтверждения.

4. Для конкурирующих объяснений выбери доступную проверку с наименьшей нагрузкой, которая может их различить. Для управляемой операции сохрани ключ шага. После обрыва проверь прежний ключ и RUN_ID. Если операция вернула `previous_check`, прочитай сохранённый результат по этому RUN_ID. Для повтора после подтверждённой остановки укажи, зачем снова читать тот же материал. При завершении объясни, какие данные достаточны для вывода или чего ещё не хватает.

Если пользователь спросил о ходе проверки или вернулся в чат после перерыва, вызови `investigation-progress ID` или `techexpert_investigation_progress`. Возьми из `resume` статус оценки и метки материалов. Если известна предыдущая ревизия, [сравни её с текущей](references/mcp.md#ход-и-продолжение-расследования). В `recent_checks` видны ревизия запуска, последняя запись, просьба остановить и подтверждение локальной остановки. При недостаточной видимости проверь прежний RUN_ID. Для содержания фактов используй разрешённое чтение по политике окружения.
Сообщение о повторе запиши через `techexpert_investigation_task` или `investigation-task` с `text`, прежним ID, ожидаемой ревизией и полем `occurrence`. Передай источник сообщения и известные границы с часовым поясом. При неопределённом результате повтори тот же ключ. Если вернулись `source_gaps`, продолжи с проверенными вложениями. Для доступной части прежнего вложения укажи его сохранённую ревизию и окно нового эпизода.
Для разрешённых вложений проверь `tj-coverage` и `jr-coverage` через `context-read` или `techexpert_context_read`. Без явно заданного окна берутся сохранённые границы эпизода. Если известна только точка во времени, уточни подходящие начало и конец с часовым поясом или передай уже согласованное окно. Для анализа выбери участки с записями и уточни недостающие данные. Совпадение временных диапазонов и наличие полей сами по себе не связывают записи с одной операцией или базой.

Для поиска в ЖР рядом с выбранной записью ТЖ используй `jr-near-tj`. Сошлись на обе записи и проверь принадлежность источников и время, если от этого зависит вывод.
Для совместной обработки нескольких согласованных представлений используй `code.context` или `techexpert_code_context`. [Программная обработка](../code-mode-analysis/SKILL.md)
Для измеренного сравнения с нормой используй sample.describe по подходящим сохранённым случаям/измерениям: проверь размер, период, условия, пропуски и разброс. Название контрольной группы и сообщение «обычно» не подтверждают её нормальность.

5. Свяжи наблюдения с доказательствами, проверь применимость знаний и объясни причину с её фактическим уровнем уверенности. Оцени отдельно применение, эффект, правильность результата, достижение цели и повторение. По одним парным замерам оставляй повторение неизвестным.

Открывай навык, нужный для следующей проверки:

- Настройка окружения, доступ и обновление — [setup-and-access](../setup-and-access/SKILL.md).
- Ход расследования — [investigate](../investigate/SKILL.md).
- ТЖ и его сбор — [tech-log](../tech-log/SKILL.md), [logcfg](../logcfg/SKILL.md).
- ЖР — [event-log](../event-log/SKILL.md).
- Кластер и RAC — [onec-cluster](../onec-cluster/SKILL.md), [rac](../rac/SKILL.md).
- СУБД — [postgresql](../postgresql/SKILL.md), [sql-server](../sql-server/SKILL.md).
- Исходники и помощь с выгрузкой — [onec-source](../onec-source/SKILL.md).
- Метрики узлов и клиентский интерфейс — [os-metrics](../os-metrics/SKILL.md), [client-ui-performance](../client-ui-performance/SKILL.md).

## Сохранение и продолжение

investigation-create/update сохраняют ход расследования, источники, факты и объяснение текущего harness. Для редкого эпизода подготовь ограниченный план сбора, сохрани awaiting_occurrence и объясни, как вернуться в тот же чат после сообщения о событии. При продолжении используй прежний ID и проверь целостность сохранённых свидетельств.

Карточки знаний — проверяемые основания: применимость, версии и статус важны перед использованием. Сохраняй knowledge-use для реально использованных заметок; пересмотри затронутые рекомендации при knowledge_review. [Детали](references/knowledge-lifecycle.md).

Для поиска передай исходный симптом в `knowledge.search` и уже известные условия в `environment`. События, которые действительно наблюдались, передавай в `events`. Для первой страницы задай `excerpt_chars: 0`, затем открой нужную карточку по ID. Условия и версии, которых пока нет, оставляй неизвестными.

Предложение случая в общую базу проходит локальный очищенный предпросмотр. Отправка конкретного материала в GitHub требует явного поручения и проверки опубликованного Issue. [Поток](references/incident-drafts.md).

## Проверка комплекта

readiness проверяет комплект без обращения к пользовательским источникам; doctor обнаруживает инструменты. Их актуальные результаты переиспользуются в той же сессии. При проверке из агента передай хеш фактически прочитанной точки входа; это заявленное подтверждение harness. [Детали первого запуска](references/first-run.md).

demo — отдельная необязательная проверка на комплектном синтетическом примере. Специальный профиль SC-01 применяй только к соответствующим данным или при явном запуске примера; его описание находится в [профиле проверки](../investigate/references/sc01.md). Состав подтверждённых адаптеров и форматов задаётся фактическим каталогом, а не сходством симптома с примером.

Если harness настроен на MCP, используй [его контракт](references/mcp.md) с теми же данными и пределами. Поддержка конкретного клиента и способа исполнения подтверждается отдельно. Общий механизм расследования не зависит от названия контрольного примера.
