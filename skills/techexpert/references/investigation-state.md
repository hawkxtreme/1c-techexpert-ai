# Состояние расследования

Агент готовит request/patch в частном временном каталоге из уже известного диалога. Пользователь не обязан писать JSON. Все команды выполняются с одним `--state-dir`, если его переопределили; аргумент располагается перед подкомандой. Идентификаторы случаев/артефактов/сравнений получают из реальных результатов CLI.

`templates` возвращает TPL-00–TPL-10 и сохранённые в выбранном частном состоянии варианты USR-…. `template TPL-01 --variant document-posting --database-mode file --time-mode past` выдаёт вопросы, источники, проверки и ограничения. SQL/RAC исключаются для file/unknown. Наличие шаблона не означает реализации всех сценариев и Testpilot.

## Сохранить свой вариант

По просьбе пользователя агент готовит JSON вне репозитория. Выбери реальную базовую ревизию из `templates`; пример для текущего TPL-00:

```json
{
  "id": "USR-my-check",
  "base_template_id": "TPL-00",
  "base_template_revision": 1,
  "title": "Моя повторяемая проверка",
  "questions": ["Какое действие выполняется и когда результат готов?"],
  "sources": ["tj", "jr", "os", "source"],
  "checks": ["source-coverage"],
  "defaults": {"time_mode": "unknown", "scale": "unknown"}
}
```

`template-save request.json --expected-revision 0` создаёт USR-my-check. ID выбирается один раз: USR- и до 48 строчных латинских букв, цифр или дефисов, начиная с буквы/цифры. Для изменения того же варианта передай `id` и изменяемые поля, например `{"id":"USR-my-check","title":"Уточнённая проверка"}`, с `--expected-revision 1`. Устаревшая запись отклоняется. Частичная/повреждённая запись сохраняется для разбора и не перезапускается автоматически. Хранятся до 32 вариантов, до 100 ревизий каждого и до 64 КиБ на ревизию.

При создании можно выбрать `base_variant`, например document-posting для TPL-01: его вопросы войдут в плоский пользовательский вариант. Изменяемые поля — title, applicability, questions, sources, checks, optional_fields и defaults. Списки заменяются целиком; пропущенные поля наследуются. sources принимает только известные типы; checks — названия проверок как неисполняемые метки; optional_fields — известные поля комплектного каталога. defaults принимает только time_mode, scale и database_mode с их штатными перечислениями. Доступы, пути, ключи, команды и секреты в defaults не допускаются. Не помещай секреты в авторский текст; произвольная проза не сертифицируется как свободная от них.

`template USR-my-check --revision 1` читает точную сохранённую версию. Для нового расследования передай `template_id` и `template_revision`. Неуказанные время, масштаб и режим ИБ могут получить предложенные defaults; явный unknown остаётся unknown. Эти значения — настройки пользователя, а не наблюдение реальной базы. При продолжении ответы не сбрасываются; для выбора другой версии передай template_id/template_revision в investigation-update. Сохранённый в расследовании снимок не зависит от дальнейшего изменения или утраты пользовательского каталога. GUI различает текущий вариант каталога и сохранённую ревизию расследования и передаёт именно показанную версию.

Пользовательские шаблоны хранятся в частном состоянии, не меняют комплектный каталог, не входят в пакет и не экспортируются как тело публичного инцидента. Если частный каталог недоступен, GUI показывает ошибку и позволяет продолжить с комплектными шаблонами или закреплённым снимком; историю шаблонов он не восстанавливает. CLI чтения каталога сохраняет строгую ошибку состояния. Вопросы и метки проверок не запускают инструменты, не подтверждают причину и не выдают дополнительных прав. Сохранение шаблона не подключает источники.

## Создание и контекст

`investigation-create request.json` принимает:

```json
{
  "task": "Фоновая загрузка заказов стала медленной",
  "template_id": "TPL-02",
  "time_mode": "past",
  "scale": "background",
  "episode": {"database_mode": "file", "user_reported_baseline": "Обычно пять минут; сообщение пользователя"},
  "harness": {"name": "current harness", "version": null, "model": null}
}
```

Достаточно `{"task":"описание проблемы"}`: получатся TPL-00 и неизвестные время/масштаб. Время: `unknown/past/current/reproduce`. Масштаб: `one/several/all/background/unknown`. Для TPL-01 есть необязательный `variant: document-posting`. Точные модель и версия остаются null, если harness их не сообщает. `episode` допускает description/start/end/utc_offset/database_mode/operation/user_reported_baseline/client_context; recurrence_seconds и requested_window_seconds задаются отдельно как положительные числа секунд либо null.

Вернувшийся `investigation_id` сохраняется в этом чате. `init --investigation ID` показывает уже полученное описание и сохраняет выбранный профиль/контекст новой ревизией. `investigation ID` загружает актуальную ревизию; `--revision N` — прежнюю. Ответ содержит пути `local_reports.json` и `local_reports.md`. Эти поля ответа не нужно помещать в patch.

## Дополнение данных

`investigation-update ID patch.json --expected-revision N` изменяет только переданные поля. Массивы заменяются целиком; сохраняйте нужные прежние элементы. Устаревший writer отклоняется: перечитайте актуальную ревизию и объедините изменения, не перезаписывая работу другого исполнителя. Исходная task не меняется; уточнение помещается в episode.

Пример связей — подставьте существующий CASE_ID и настоящее свидетельство:

```json
{
  "attachments": [{"id": "A-1", "kind": "case", "target_id": "CASE_ID"}],
  "evidence": [{"id": "E-1", "attachment": "A-1", "record": "s1:1"}],
  "facts": [{"id": "F-1", "text": "Длительность выполнения по наблюдаемым границам", "evidence": ["E-1"], "measurement": {"attachment": "A-1", "pointer": "/durations_seconds/execution"}}],
  "hypotheses": [{"id": "H-1", "text": "Проверяемое объяснение", "status": "proposed", "evidence": ["E-1"]}],
  "open_questions": ["Есть ли сравнимый нормальный запуск?"]
}
```

Attachment kind: case/artifact/comparison. Для case `record` — существующий evidence_id; для artifact — sN, для native-jr также sN:rN; для comparison — `report`. Создание/чтение проверяет сохранённые отчёты и снимки. F-измерение получает scalar `value` по JSON pointer из отчёта инструмента, не из ответа модели. Null остаётся неизвестным. Текст факта имеет basis утверждения harness со ссылками; семантика текста инструментом не доказана.

Гипотезы: proposed/testing/supported/refuted/insufficient_data; supported/refuted требуют доказательств. Contradictions: id C-…, text, evidence, hypotheses, status unresolved/resolved и resolution при разрешении. Обе позиции сохраняются; unresolved противоречие выбранной гипотезе блокирует confirmed.

## Объяснение и результат

Поле assessment содержит summary, cause_state, evidence, limitations, recommendations, references. Для hypothesis/confirmed нужны hypothesis_id и mechanism. Для confirmed требуются supported-гипотеза, verification и непустой массив alternatives. Это проверка структуры, а не независимое суждение о причине. Указывайте область применимости и не называйте синтетические или лабораторные наблюдения производственным случаем.

Рекомендация: id R-…, kind diagnostic/lab_change/production_change, basis (E-/H-ID), goal, prerequisites, expected_effect, verification, limitations. Для изменения также risk/rollback. Reference: credential-free HTTPS url, purpose, applicability; ссылка не становится подтверждением механизма только по факту включения.

execution_status: completed/partial/error/cancelled, отдельно от cause_state: confirmed/hypothesis/insufficient_data. Изменение эпизода, доказательств, гипотез, шаблона, времени/масштаба или профиля делает прежнее assessment неактуальным без явно переданной новой интерпретации. Старые отчёты остаются. Смена текущего harness сама не переписывает автора предыдущего assessment.

improvement хранит независимые признаки:

- applied: proposed/reported/evidenced;
- comparability: comparable/not_comparable/unknown;
- effect: better/no_confirmed_change/worse/unknown;
- goal: reached/not_reached/unknown;
- recurrence: observed/not_observed_in_window/unknown;
- window: описание точного окна либо null, evidence: E-ID.

Отсутствие повторения требует окна и свидетельств. Ускорение не доказывает достижения цели. Изменение основания снимает старое improvement с текущей ревизии, сохраняя его в истории.

## Этапы и возвращение после повторения

workflow_stage: initial_analysis/prepare_observation/awaiting_occurrence/analyze_episode/verify_fix/closed. При периодическом инциденте сначала подготовьте конкретный способ сбора. observation_plan содержит operations, sources, metrics, необязательные thresholds, duration_seconds, max_bytes, responsible, rollback, verification, status и при наличии evidence. Дополнительные start/end требуют часового пояса и согласованной длительности; collection_method/rotation описывают способ, collection_state отделяет unknown/not_started/launch_reported/receiving_data/stopped_reported. Статус плана: proposed/configured_reported/data_verified/cancelled; для data_verified и receiving_data требуются доказательства.

Окно плана — до семи суток, отдельно от одного ОС-запуска до 30 минут. Запись суточного плана не запускает и не реализует суточный коллектор. Укажите реальные средства источников/оператора, достаточное место, ротацию и остановку. Сам план и tool_runs в этой версии хранят описание и учёт; они не являются общим исполнителем и не обеспечивают глобальный контроль расхода harness.

При сообщённой/проверенной подготовке сохраните `workflow_stage: awaiting_occurrence`; ответ будет partial для расследования и completed для этапа подготовки. continuation указывает внешний триггер и model_polling_required=false. Завершите текущий этап: дайте пользователю ID, что готово, ограничения запуска и как вернуться в этот же чат после сообщения о событии. Не держите модель в ожидании и не выдавайте короткий сбор за проверку суток.

После сообщения пользователя или внешнего мониторинга загрузите тот же ID и передайте patch:

```json
{
  "occurrence": {
    "source": "user",
    "message": "Мониторинг сообщил о повторении; точное время пока неизвестно",
    "started_at": null,
    "ended_at": null,
    "evidence": []
  }
}
```

source: user/external_monitoring. Время при наличии требует смещения. Автоматически добавляется время приёма сообщения и этап analyze_episode; сообщение имеет status reported_not_verified. После проверки собранного эпизода evidence и link_basis описывают связь, статус становится evidenced_by_harness. Это не независимое подтверждение связи инструментом. Подключите новые снимки, проверьте покрытие и продолжайте анализ/проверку исправления в прежней истории.

## Ограничения сохранения

До 1000 ревизий, 16 attachments, 200 evidence/facts, 100 hypotheses/contradictions/tool_runs; документ/Markdown до 2 МиБ. Input patch до 1 МиБ. Состояние частное; report не обезличен для внешней отправки. Учёт затрат tool_runs сообщён harness, токены неизвестны при отсутствии фактического счётчика. Receipt и head записываются последними; незавершённая ревизия не подменяет прежнюю. Автоматического удаления lock/прерванной ревизии нет: сохраните материалы и проверьте владельца до восстановления, не обходите guard принудительно.


## Принадлежность использованных источников

Новые расследования сохраняются со schema_version:2. Schema1 остаётся читаемой без перезаписи; явное редактирование создаёт новую ревизию schema2. Исторические отчёты, автор объяснения и сохранённые выводы не заменяются проверкой принадлежности.

Если вывод связывает два материала, агент добавляет source_bindings: id S-…, attachment A-ID, необязательные profile_source_id и base_id, record_source для выбранного s-ID, applicability с start/end либо null и reported с явно сообщёнными сведениями. profile_revision закрепляется автоматически; при смене общего профиля старые привязки сохраняют свою ревизию. Новый выбранный профиль требует явного переподключения конкретного источника. passport вычисляется по сохранённым данным; его нельзя подменять входным утверждением observed. Агент готовит patch, пользователь не пишет JSON.

Профильные псевдонимы, режим ИБ, адреса и имена SQL-баз остаются reported. Наблюдение содержит указатель и хэш проверенного отчёта. UUID последовательного ЖР и повторяемый номер сеанса не устанавливают ИБ/узел/эпоху. Версия/commit исходников относится к статическому снимку, не к рабочей конфигурации и расширениям. Неизвестные факты остаются null; конфликт сохраняет обе позиции. Применимость задаётся отдельно от времени чтения; даты требуют известного смещения. Наличие смещения ещё не подтверждает синхронизацию узлов.

source_links содержит id L-…, left/right S-ID, claim и необязательный reported:true для сообщения пользователя. Поддержаны same_infobase, same_snapshot, same_source_version, same_run. check вычисляется: одинаковые байты подтверждают только снимок; Git commit — только статическую ревизию; same_run может подтвердить только сохранённое окно проверенных маркеров. Это не длительность всего задания, принадлежность другим узлам или независимая проверка рабочей ИБ. Всегда читай scope, exact_correlation_allowed и отдельный runtime_correlation_allowed. Совпадающее имя/SQL/время служит поиску кандидата. Полностью нормализованный профиль общих сущностей окружения ещё не реализован.

Факт, гипотеза и рекомендация могут содержать source_links:[L-ID]. Контекст показывает зависимые F/H/R и assessment; неизвестная/спорная связь требует пояснения только для зависящего вывода. Отсутствие декларации зависимости остаётся неизвестным, а не автоматически проверенной независимостью. source-context ID --revision N читает только сохранённую ревизию; общий управляемый маршрут — investigation.sources с investigation_id/revision, через MCP techexpert_investigation_sources. В CodeMode scope.investigations содержит точные {id,revision}. Не повторяй сбор при чтении или после повреждения снимка.

Изменение привязки входит в основание анализа и делает старое assessment неактуальным в новой ревизии. Старый вывод остаётся в истории. Публичный черновик по policy10 содержит только сводку неподтверждённых связей; сами паспорта, частные доказательства, исходные logcfg/XML/diff и новые значения идентичности не экспортируются. Для прежнего черновика нужна новая подготовка и просмотр точных файлов.
