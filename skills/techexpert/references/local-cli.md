# Локальный CLI

[Покрытие ТЖ](source-coverage.md): `source-check MANIFEST` читает явно выбранные входы без сохранения состояния, `coverage CASE_ID` проверяет сохранённые снимки без обращения к исходным путям. Новые analyze содержат source_coverage; наличие данных и полнота/принадлежность различаются.

Первый запуск использует [readiness и отдельный безопасный demo](first-run.md). `readiness [--entrypoint-sha256 HASH] [--investigation ID]` ничего не подключает и не сохраняет; init возвращает тот же отчёт. Повреждённый комплект даёт exit2, отсутствие подтверждения входа требует текущего агента. Последний явный demo доступен в `demonstration`; отчёт сохранён отдельно от рабочего расследования.

Если готовых XML/BSL нет, [помощник выгрузки](source-export.md) задаёт `source-export-plan`, отдельно выбранный `source-export`, проверку `source-export-status` и сохранение готового пути через `profile-save --expected-revision`. Сохранение профиля остаётся настройкой и не запускает native-операции.

## Ревизии расследования

Для `templates`, `template`, `investigation-create`, `investigation-update`, `investigation` и продолжения после сообщения о повторении используйте [контракт состояния](investigation-state.md). Это дополнение к immutable `case_id`, `artifact_id` и `comparison_id`; оно не заменяет их сырые доказательства. `init --investigation ID` получает контекст из того же сохранённого расследования.

Предложение инцидента для базы знаний использует отдельные `incident-draft`, `incident-preview`, `incident-edit`, `incident-export`, `incident-send-plan` и `incident-record-submission`; [точный контракт](incident-drafts.md) отделяет локальную подготовку от явно порученной внешней отправки текущим harness.

Команды выполняются из проверенного корня пакета. `python` ниже означает рабочий интерпретатор Python в среде пользователя; при необходимости используй его полный путь. Корневой `techexpert.py` и его локальные модули должны поставляться вместе со skills.

```text
python techexpert.py doctor
python techexpert.py init
python techexpert.py profile
python techexpert.py demo
python techexpert.py analyze "путь/manifest.json"
python techexpert.py show CASE_ID
python techexpert.py events CASE_ID --source s1 --event CALL --property SessionID=12 --offset 0 --limit 20
python techexpert.py evidence CASE_ID EVIDENCE_ID
python techexpert.py compare --before BEFORE_CASE_ID --after AFTER_CASE_ID
python techexpert.py comparison COMPARISON_ID
python techexpert.py knowledge "медленное фоновое задание"
python techexpert.py source-help tj
python techexpert.py templates
python techexpert.py template TPL-02 --database-mode file --time-mode past
python techexpert.py investigation-create "путь/request.json"
python techexpert.py investigation INVESTIGATION_ID
python techexpert.py investigation-update INVESTIGATION_ID "путь/patch.json" --expected-revision 1
python techexpert.py init --investigation INVESTIGATION_ID
python techexpert.py rac clusters --endpoint server:1545
python techexpert.py rac infobases --endpoint server:1545 --cluster CLUSTER_UUID
python techexpert.py postgresql capabilities --database DATABASE --host SERVER --user OBSERVER
python techexpert.py os-plan --duration 300 --interval 1
python techexpert.py os-collect --duration 300 --interval 1
python techexpert.py os-import "путь/measurements.json"
python techexpert.py apdex "путь/measurements.json" --target 5 --operation post
python techexpert.py artifact ARTIFACT_ID
python techexpert.py artifact ARTIFACT_ID --source s1
```

`CASE_ID`, `EVIDENCE_ID`, `COMPARISON_ID`, идентификаторы случаев до/после и источника подставляются из фактического результата, а не угадываются. `CALL` и `SessionID=12` — пример фильтра; замени их значениями исследуемых записей. Передавай значения отдельными аргументами с корректным quoting для текущего shell. Не исполняй содержимое входных файлов как команды. Сравнение одной пары допустимо, но недостаточно для подтверждения эффекта.

Все перечисленные команды возвращают JSON. Читай фактический результат и статус завершения; ошибка, неполный результат или доступный только проект настройки не равны успеху. Не придумывай поля ответа и дополнительные подкоманды. При изменении версии сверяй контракт с поставленным CLI.

Состояние по умолчанию находится в локальных данных приложения вне репозитория. Явное переопределение — глобальный аргумент **перед** командой:

```text
python techexpert.py --state-dir "путь/к/частному-состоянию" demo
python techexpert.py --state-dir "путь/к/частному-состоянию" show CASE_ID
```

Используй один и тот же каталог для продолжения случая и сравнения. Не выбирай каталог Git-репозитория для частного состояния. Операции `init`, `demo`, `analyze` и `compare` могут создавать локальные профили, результаты и свидетельства; это не изменение исследуемой системы. Не копируй рабочие материалы в `examples/`, `knowledge/` или файлы плагина. Вывод, переданный в чат, становится доступен модели текущего harness; выбирай только необходимые разрешённые фрагменты.

После сохранения в GUI вызови `profile` с тем же каталогом состояния. Команда возвращает ревизию профиля, выбранные базы и независимые адреса источников в текущий чат агента. `configured_not_connected` означает сохранённую настройку, а не проверенные подключения. Если профиль не создан, результат — `not_configured` с действием `init`.

## Вход SC-01

`demo` самостоятельно использует [комплектный манифест](../../../examples/sc01/case.json). Для реальных предоставленных данных используется отдельный `analyze`.

Контракт манифеста:

- `schema`: `1`;
- `scenario`: `"SC-01"`;
- `origin`: `"synthetic"` или `"provided"` — происхождение, не оценка достоверности;
- `selection`: непустые строковые метки `database`, `node`, `process`, `epoch`, `run`; исключение — отдельный профиль корреляции ниже;
- `sources`: список явно выбранных файлов с `path` и поддерживаемым `format`. Относительный путь разрешается от каталога манифеста.

Для нормализованных событий `selection` выбирает область `scope`. Для нативного ТЖ это заявленные метки эпизода: они не фильтруют нативные записи и не доказывают связь с запуском. Не присваивай им фактический смысл без свидетельств.

### Нормализованные отметки: normalized-events-v1

Входные файлы содержат JSONL: по одному нормализованному событию на строку. Событие содержит `kind` (`queued`, `started`, `finished` или `wait`), `timestamp` в ISO 8601 с часовым смещением и `scope` с теми же полями идентичности, что у `selection`. Для `wait` требуется `end`. Проверку значений, путей, интервалов и полноты выполняет CLI; ошибка проверки не исправляется выдуманным событием.

Источник имеет `format: "normalized-events-v1"`. Это внутренний контракт, не формат сырых журналов. Совпадение времени не даёт права присвоить неизвестному событию `run`, `process` или `epoch`, а длительность ТЖ не превращается в отметки `started/finished`. Если надёжной нормализации нет, сохрани ограничение.

### Нативный текстовый ТЖ: 1c-tj-text-v1

Используй [шаблон](../../../examples/sc01/native-case.template.json) в отдельном частном каталоге, заменив все `REPLACE_WITH_...`. Он содержит `origin: "provided"`, но не содержит настоящего журнала и не используется `demo`. Версию и временные сведения нужно подтвердить для самого источника.

Обязательные поля каждого нативного источника:

| Поле | Значение |
| --- | --- |
| `path` | Путь к стабильному снимку текстового файла; сжатые файлы не поддержаны |
| `format` | `"1c-tj-text-v1"` |
| `platform_version` | `"8.3.27.1989"`; другие версии не входят в этот профиль |
| `encoding` | `"utf-8"`; ошибочные байты не заменяются догадками о кодировке |
| `placement` | `"folders"` либо `"plain"` |
| `timestamp_format` | `"minute"` либо `"iso"`, явно по настоящему заголовку записи; не выводится из `placement` |

Для `timestamp_format: "minute"` запись начинается коротким временем, например `45:00.000001-2460000000,CALL,...`. При любом `placement` обязательны `rotation_hours: 1` и `file_hour`: ISO 8601 с явным часовым смещением, точно на начало часа, например `2026-11-15T09:00:00+03:00`. Числа иллюстративные. Не угадывай век и часовой пояс по имени `yymmddhh.log`, не применяй этот профиль к многочасовому файлу.

Для `timestamp_format: "iso"` в начале каждой записи должна быть полная дата, например `2026-11-15T09:45:00.000001-2460000000,CALL,...`. При любом `placement` требуется `utc_offset` источника. Только если фактический файл имеет такой заголовок, вместо полей `file_hour` и `rotation_hours` используй такой объект источника:

```json
{
  "path": "REPLACE_WITH_NATIVE_TJ_SNAPSHOT_PATH",
  "format": "1c-tj-text-v1",
  "platform_version": "8.3.27.1989",
  "encoding": "utf-8",
  "placement": "plain",
  "timestamp_format": "iso",
  "utc_offset": "+03:00"
}
```

`+03:00` — пример; подставь подтверждённое смещение источника за период. Не используй часовой пояс текущего ПК автоматически. `plain` не гарантирует полную дату: локальная проверка 8.3.27.1989 с часовым периодом по умолчанию получила короткое время при таком размещении. Профиль должен соответствовать реальным заголовкам; автоматического выбора `timestamp_format` нет. Необязательный `context` принимает только строковые `node`, `process`, `epoch` и сохраняется как `user_declared_not_verified`. Эти метки не подменяют свойства записи и не устанавливают корреляцию.

Результат отделяет `native_observations` от нормализованной шкалы задания. `job_correlation: "not_established"` сохраняется и при смешанном манифесте. Время записи и `duration_us` не используются для универсального вычисления начала операции. Без независимых отметок очередь, выполнение и общее время задания неизвестны. Успешный разбор текста не равен подтверждённому расследованию рабочего SC-01.

### Контролируемое файловое задание: 1c-file-job-markers-v1

Это явный профиль **Windows, файловая ИБ, 8.3.27.1989, процесс 1cv8** с инструментированным обработчиком. Он не подходит произвольным журналам без независимых свидетельств. [Лабораторная конфигурация](../../../examples/sc01/lifecycle-probe/README.md) и [обезличенный реальный пример](../../../tests/fixtures/job-lifecycle/completed.json) показывают проверенный контракт. Изменение рабочей конфигурации не входит в `analyze` и не разрешается этим примером.

Манифест задаёт `correlation_profile: "1c-file-job-markers-v1"` и **только** `selection: {"run": "фактический UUID задания"}`. Выдумывать node/PID/epoch для этого входа не требуется: неизвестные поля остаются `null`. В `sources` разрешены `1c-tj-text-v1` и `1c-job-runtime-v1`, а с явным `workload_profile` — дополнительные форматы ниже; смешивать с нормализованными отметками нельзя. Для каждого runtime-файла обязательны `platform_version: "8.3.27.1989"`, `platform_utc_offset` и `role` — `controller`, `worker_enter` или `worker_exit`. `+03:00` является примером; смещение подтверждается для исходного компьютера и периода. Роли одного запуска уникальны, UUID и nonce должны совпадать. Второй запуск оформляется отдельным манифестом, даже если ТЖ общий.

Runtime — UTF-8 JSON, до 1 МиБ на файл, `schema: 1`, `origin: "controlled_real_background_job"`. Его содержимое остаётся недоверенным; хэш доказывает сохранность снимка, не подлинность источника. Повторяющиеся ключи JSON отвергаются. Контроллер содержит `job_uuid`, `nonce`, `connection_string` и `final_job_snapshot`: UUID, канонический `job_state_code`, `job_begin_platform_date`, `job_end_platform_date` для завершённого задания, `platform_date_precision: "seconds"`, независимое время наблюдения. Объект задания перечитывается после ожидания. Локализованная строка состояния и флаг `completed` не заменяют канонический enum.

Снимок входа обработчика содержит его настоящий UUID, nonce, `session_id`, `session_info_number`, соединение и время наблюдения; выход — тот же UUID/nonce/session_id и время. UTC-поля: `observed_utc_ms`, `clock_epoch: "0001-01-01T00:00:00Z"`, `clock_precision: "milliseconds"`, согласованное `observed_utc_seconds`. Это не Unix epoch. Контрольные SDBL-запросы содержат точный текст `SC01LIFECYCLE:body_enter|body_exit:<nonce>:<UUID>` в формате примера. Простое упоминание UUID в SQL/Context не устанавливает связь.

В `job_correlation` независимы два результата:

- `job_lifecycle`: `status`, UUID, состояние `active/completed/failed/canceled`, начало/конец, разность с секундной точностью и консервативными `execution_bounds_seconds`, ссылки на снимки. Очередь и общее время неизвестны: `submit_requested` не доказывает постановку во внутреннюю очередь.
- `native_link`: `status`, идентичность сеанса, два маркера, участок байтов, наблюдаемое время тела и отдельный интервал SESN. Привязка относится только к прочитанным записям между маркерами в одном снимке и потоке. Предпросмотр ссылок ограничен 200, полный `linked_count` и `linked_evidence_truncated` явные.

Статусы `not_established/conflicting` не превращаются в диагноз. Завершившееся с ошибкой задание без снимка выхода сохраняет подтверждённый lifecycle, но не получает доказанную выборку тела. Потерянные записи, смена сеанса, неоднозначные свойства идентичности или противоречивые источники снимают связь. Номер сеанса не равен connection_id; Key допускает повторное использование.

Точное соответствие UUID/nonce/сеанса и порядка байтов устанавливает идентичность независимо от синхронизации часов. `native_link.clock_alignment.status` всегда `not_verified`; `containment_at_1ms_resolution` и подписанные разности native/runtime являются наблюдениями, не оценкой поправки часов. При расхождении порядка есть `cross_clock_order_disagreement`. Нельзя склеивать эти временные шкалы или объявлять часы синхронизированными из-за формата с микросекундами. Внутри каждой шкалы по-прежнему проверяется порядок; рассогласованные идентификаторы не допускаются.

`events CASE_ID --linked-run --offset 0 --limit 20` фильтрует по доказанной связи с выбранным UUID; дополнительны точные `--event`, `--property`, `--source`. При отсутствии связи возвращаются ноль записей и её статус, без перехода к общей выборке. Пагинация работает и за пределами 200 ссылок отчёта. `evidence CASE_ID sN:1` для runtime возвращает целый JSON-документ с границами байтов, возможным `truncated` и проверкой хэша; строка 2 не является отдельным runtime-свидетельством.

### Загрузка заказов: sc01-order-load-v1

Дополнительное поле манифеста `workload_profile: "sc01-order-load-v1"` допустимо только вместе с `correlation_profile: "1c-file-job-markers-v1"`. Выбранный UUID, отдельные runtime-снимки и нативный ТЖ сохраняют описанный выше контракт. Это контролируемый опыт **Windows, файловая ИБ, 8.3.27.1989**, не универсальная совместимость с рабочими конфигурациями.

К `sources` добавляются явно выбранные файлы с `path` и точным `format`:

| Формат | Назначение |
| --- | --- |
| `sc01-orders-csv-v1` | Фактический CSV входных заказов; проверяются его байты, строки и соответствие runtime-снимкам |
| `sc01-http-service-v1` | JSON контролируемого сервиса: каталог, политика задержки и журнал запросов данного запуска |
| `sc01-run-capture-v1` | JSON запускателя: UUID/nonce, платформа и ИБ, исходный seed, хэши входа, модуля 1С и реализации сервиса, исход процесса |
| `1c-source-text-v1` | Снимок UTF-8 исходного модуля 1С; проверяется хэш, содержимое доступно агенту для анализа и не исполняется CLI |

Для каждого дополнительного формата нужен один соответствующий снимок запуска. Дополнительные файлы — UTF-8, до 1 МиБ каждый; JSON требует объект `schema: 1` без повторяющихся ключей. Не конструируй фиктивные runtime-отметки или отчёт запускателя для заполнения пробелов. `parse_status: captured` означает сохранённый вход; смысловую проверку выполняет `order_load`. Профиль проверяет собственный ограниченный контракт, а не произвольные HTTP-журналы.

`analyze` добавляет в сохранённый случай `order_load`:

- `status`: `observed`, `partial` или `not_verified`; `scope: controlled_windows_file_8.3.27.1989`. `mode` — метка варианта из входных данных, которая не определяет успешность и не объясняет причину.
- `workload_signature`: `input_sha256`, `catalog_revision`, `catalog_sha256`, `row_count`, `service_delay_ms`, `database_seed_sha256`, `observed_computer_name`, `service_module_sha256`, платформа, путь ИБ и свидетельства. Имя компьютера согласуется между runtime-снимками; это наблюдаемая метка, не доказанный физический node ID.
- `result_validation`: `matches_expected|mismatch|not_verified`, количества, ожидаемый и фактический хэши бизнес-строк, расхождения и свидетельства. Проверяются `order_id`, `sku`, `qty`, `price`, `amount`, `catalog_revision` по CSV, каталогу и независимо прочитанным контроллером результатам ИБ. Равное число документов само по себе недостаточно.
- `external_calls`: `verified|not_verified`, количество, уникальные SKU, повторные обращения, отдельно суммы клиентских и серверных интервалов. Запросы связываются по request ID, UUID и nonce, не по близости времени. Эти суммы не являются временем задания, его ожиданием или общим интервалом по разным часам.
- `capture_validation`: согласованность отчёта запускателя, исходных данных и кода. Хэш состояния ИБ перед запуском должен совпасть с seed; хэш модуля — со снимком исходника. `capture_runner_attested` сохраняет происхождение утверждений: это проверка предоставленных данных, не независимое доказательство их подлинности.
- `load_duration_ms` и `load_duration_evidence`: отдельное наблюдение runtime; не заменяет секундную длительность полного задания. `limitations` сохраняет неполные или противоречивые проверки по компонентам.

HTTP-свидетельства в этом профиле получены от клиента и сервиса. Наличие исходящего HTTP-события в нативном ТЖ не подтверждено; ТЖ и runtime устанавливают связь с запуском, но не заменяют HTTP-снимки. CLI не устанавливает причину: агент проверяет код, факты запросов, бизнес-результат и эффект изменения. Контролируемое воспроизведение механизма не подтверждает буквальные 45 минут рабочего инцидента.

### Сохранённое сравнение до и после

`compare` принимает от 1 до 20 сохранённых `case_id` в каждой группе. Передай пары в согласованном порядке: первый `--before` сопоставляется с первым `--after` и так далее. Например, после пяти измеряемых пар:

```text
python techexpert.py compare --before B1 B2 B3 B4 B5 --after A1 A2 A3 A4 A5
python techexpert.py comparison COMPARISON_ID
```

`B1`…`B5`, `A1`…`A5` — заменяемые идентификаторы, не названия вариантов. Чередование порядка исполнения до/после организует разрешённый план опыта; `compare` ничего не запускает. Заранее отделяй прогревочные прогоны от измеряемой серии. Не удаляй из серии неудачные или неудобные результаты: все переданные случаи остаются в сравнении с причинами ограничений.

Для сопоставимости требуются разные UUID и case_id всех запусков, подтверждённое завершение задания и связь ТЖ, полный профиль `order_load`, одна платформа и путь ИБ. Во всех случаях должны совпадать хэши входа, каталога, исходного seed ИБ и реализации сервиса, ревизия каталога, число строк, задержка сервиса и наблюдаемое имя компьютера без учёта регистра. Отсутствие имени или хэша сервиса остаётся неизвестностью; совпадение имени не доказывает физическую идентичность компьютера. Исходное состояние тестовой ИБ восстанавливается перед каждым измеряемым запуском в рамках согласованного плана и отражается в отчёте запускателя. Хэш бизнес-модуля 1С может измениться как часть исправления; хэш сервиса должен остаться одинаковым, чтобы не подменить исследуемый эффект.

Результаты разделены:

- `comparability.status`: `comparable|not_comparable`; неизвестные условия не считаются одинаковыми.
- `performance.status`: `improved|inconclusive|not_comparable`. Основа — `platform_job_execution_seconds`, точность 1 секунда и точные границы `[max(0, d - 1), d + 1]` для длительности `d`. Для подтверждения нужны минимум пять полных пар, в **каждой** нижняя граница до строго больше верхней после, а `1 - median(upper_after) / median(lower_before)` не меньше 0.5. Нулевой знаменатель оставляет оценку неизвестной. Нехватка повторов даёт `insufficient_repeats` в ограничениях и не подтверждает эффект.
- `result_correctness.status`: `matches_expected|mismatch|not_verified`; все ожидаемые бизнес-результаты должны совпадать, объём записанной работы — сохраниться. Более быстрое выполнение с неверными данными не является проверенным исправлением.
- `external_calls`: проверенные количества до/после и их медианы; неизвестные значения остаются `null`. Само уменьшение числа обращений не доказывает причину или правильность результата.
- `load_observations`: отдельные миллисекундные наблюдения, без подстановки в платформенные границы.

Общее `status: verified` требует сопоставимости, успешного критерия скорости, правильного результата и проверенных HTTP-наблюдений. Прочитай также `provenance`: происхождение каждой группы и каждого случая (`synthetic`, `provided`, `mixed` или `unknown`) не теряется. `verification_scope` различает `synthetic_calculations_only`, `provided_evidence_only` и `mixed_or_unknown_evidence_only`; даже `verified` на синтетических данных не означает реальный эксперимент. `origin_authenticity_verified: false` остаётся явным и для `provided`. `cause: null`, `requires_ai_interpretation: true` сохраняют роль текущего агента в объяснении причины.

Результат содержит `comparison_id`, ссылки на все случаи, пары, свидетельства метрик и ограничения. Он сохраняется в частном состоянии под `comparisons/<comparison_id>/` как `report.json`, `report.md` и `receipt.json`. При создании проверяется целостность всех исходных случаев и их снимков. `comparison COMPARISON_ID` повторно проверяет сохранённое сравнение, его Markdown и исходные отчёты со снимками; изменение входа не принимается молча. Для деталей используй `show CASE_ID`, `evidence CASE_ID EVIDENCE_ID` и `events CASE_ID --linked-run`. Команды не изменяют исследуемую 1С и не требуют повторного согласования уже разрешённого чтения.

### Выборка и проверка свидетельств

`events` читает нативные записи из сохранённых снимков. Фильтры `--event` и `--property NAME=VALUE` задают точное совпадение, не регулярное выражение и не поиск подстроки. `--source` ограничивает выборку одним источником. `--offset` — число пропускаемых совпадений, начиная с 0; `--limit` — от 1 до 100. Следующую страницу запрашивай с возвращённым `next_offset`; `null` означает конец текущей выборки.

Ответ содержит `matched_count`, `next_offset`, `records` и идентификаторы свидетельств. Число совпадений относится к доступным разобранным записям; оно не учитывает неизвестные события, отфильтрованные настройками платформы, и не доказывает полноту периода. Проверяй `parse_status` источников и `limitations` отчёта. Пустой файл, ошибочный формат, частичный разбор и отсутствие совпадений имеют разный смысл.

`evidence` проверяет хэш сохранённого снимка. Для нативного ТЖ возвращается логическая запись с `line`, `end_line`, `byte_start`, `byte_end`: многострочный контекст относится к одной записи, идентификатор соответствует её начальной строке. Для runtime, сервиса и отчёта запускателя `sN:1` адресует целый JSON-документ. Для CSV и исходного модуля команда возвращает выбранную физическую строку; ссылка `sN:1` не означает показ всего такого файла. При `truncated: true` текст показан не целиком. Не превращай продолжение строки в отдельное событие и не восстанавливай скрытый текст по агрегатам.

Пределы локального входа: до 32 файлов, 16 МиБ на файл журнала, 1 МиБ на runtime или дополнительный файл, 64 МиБ суммарно, 100 000 записей журнала и 256 КиБ на запись. Ограничение, ошибка чтения или изменение файла при снятии снимка не означают отсутствия событий. Подготовь меньший стабильный снимок нужного периода, сохранив полные логические записи и сведения о его происхождении. Подробнее о допустимых выводах — [границы нативного SC-01](../../../knowledge/cases/SC01-native-tj-boundaries.md).
