# Каталог и сохранённый запуск операции

Это средства текущего агента, а не требование к пользователю писать JSON. Сначала выбери проверку и согласованные источники/пределы из задачи, затем сам подготовь частный запрос. Сохранение GUI не вызывает эти операции. ИИ интерпретирует результат отдельно; `succeeded` не означает подтверждённую причину или полноту источника.

```powershell
python techexpert.py capabilities
python techexpert.py capabilities case.analyze
python techexpert.py --state-dir "D:/private/techexpert-state" operation-run "D:/private/sc01-request.json"
```

Каталог содержит исполняемые схемы аргументов и результата, источники, права, область, предел времени/результата и влияние. Дополнительные свойства, произвольные команды, исполняемый код и секреты не принимаются. Доступы остаются у текущего пользователя ОС; executor_id — заявленная метка harness, не проверенная учётная запись или новая выдача прав.

Пример запроса, который агент сохраняет до первого вызова:

```json
{
  "schema_version": 1,
  "operation_key": "sc01-first-import-unique-plan-id",
  "executor_id": "current-harness-session-id",
  "operation": "case.analyze",
  "arguments": {"manifest": "D:/private/incident/manifest.json"},
  "budget": {"timeout_seconds": 60, "max_result_bytes": 16777216}
}
```

max_result_bytes относится ко всему возвращаемому JSON в UTF8/LF, включая служебные поля и завершающий перевод строки. Первый ответ имеет replayed:false; повторное чтение — replayed:true. Если текущие предупреждения на повторе перестали помещаться, выдача имеет status:partial, execution_status прежнего запуска, data_omitted:true и truncated:true. Это усечение текущего представления, а не повторная обработка или изменение сохранённых фактов. Не запускай импорт/сбор заново для восстановления пропущенного текста.

Ключ обозначает один согласованный шаг. Создай и сохрани его перед запуском; после потери ответа используй тот же файл/ключ. Другой executor может прочитать этот запуск. Смена аргументов, бюджета или ожидаемой ревизии с тем же ключом даёт конфликт. Для действительно нового сбора нужен отдельный шаг и новый ключ в пределах уже разрешённого плана; не меняй ключ, чтобы обойти неизвестный исход старого запуска. Повтор не открывает оригиналы и не создаёт второй case/artifact. Числа и ссылки сохранённого результата проверяются по удержанным свидетельствам; порча не вызывает новый импорт. Текущий current_knowledge_review добавляется отдельно при чтении, исходная data и прежний файл не переписываются; прежняя data.knowledge_review относится к моменту того вычисления.

Необязательный context задаёт investigation_id и expected_revision. Перед стартом сверяются ревизия и хэш; запрос с устаревшей ревизией не запускается. Сбор сохраняет свой контекст, даже если в это время меняется профиль/расследование. Полученный case_id/artifact_id/comparison_id подключай к Investigation отдельным обычным update с актуальной ожидаемой ревизией, не переписывая чужие изменения.

```powershell
python techexpert.py operation-status RUN_ID
python techexpert.py operation-result RUN_ID
python techexpert.py operation-cancel RUN_ID --executor-id current-harness-session-id
python techexpert.py operation-reconcile RUN_ID
```

Run_id — 64 шестнадцатеричных символа, отдельный от 32-символьных ID свидетельств. Состояния preparing/starting/running/stopping означают подготовку, записанный дочерний процесс, подтверждённый вход исполнителя и остановку. Запрос отмены хранится отдельно. Только stop_verified подтверждает локальную остановку; старый heartbeat сам по себе этого не доказывает. CLI возвращает JSON; журнал этапов хранится частно в operations/RUN_ID/journal.jsonl. Коды нового маршрута: 0 выполнено, 1 частичный/ожидающий/прерванный результат, 2 неверный вход, 3 ошибка исполнения, 130 отмена. Недостаточность данных для причины не является ошибкой исполнения инструмента.

Reconcile получает системную блокировку записи и проверяет реальные PID вместе с временем создания/эпохой, ОС и областью PID. Чужая ОС, другой Linux PID namespace или неизвестная область не позволяют подтвердить остановку. При живом или неизвестном владельце не забирает работу. Если процесс завершился и оставил целый запечатанный результат при тех же совместимых версиях правил, завершается только перенос в штатное частное хранилище; вычисление не повторяется. Если последний receipt не удалось записать, status показывает incomplete_commit; после исправления доступа явный reconcile может завершить только запись/проверку готовых файлов без нового исполнителя. Прежняя ошибка остаётся в журнале и recovery_previous_reason, а не выдаётся за новую причину остановки. Без запечатанного результата сохраняется прерванное состояние. Повреждение, неизвестная группа процессов и неподдержанный профиль требуют разбора; не удаляй lock/state для обхода. В Linux смерть ведущего процесса не доказывает остановку группы; неполная видимость процессов остаётся неизвестной.

Штатная отмена локального ОС-сбора даёт короткую паузу на сохранение частичных отсчётов. Затем останавливается только собственное дерево. После аварии несохранённая память не восстанавливается; удержанные файлы не выдаются за готовый отчёт. Windows требует подтверждённую поддержку FileRenameInfoEx/POSIX semantics для частного состояния (проверено на местном NTFS), использует Job с kill-on-close и пределом памяти; Linux — отдельную сессию, ограничение адресного пространства и собственный watchdog исполнителя. При закрытии модели пределы не требуют её опроса. После обрыва SSH/WinRM подтверждается только местная часть; завершение удалённого процесса остаётся неизвестным, его штатный probe ограничен переданной длительностью.

Общие пределы: результат до16MiB, память1GiB (весь Windows Job / адресное пространство каждого Linux-процесса; общий пик Linux-дерева не измерен и не ограничен этим пределом), собственные файлы до256MiB/1000членов, свободное место не ниже10GiB на выбранном томе состояния. Диск и вывод проверяются периодически, возможен ограниченный выброс между проверками. Исполнитель имеет свой timeout, после него допускается до3с на остановку; приём запроса, повторное чтение и финальная проверка/запись управляющего процесса пока не имеют отдельного жёсткого лимита процесса и не входят в замер пика памяти исполнителя; ОС-пресет300с/1с изменяем, максимум1800с. Замеры отделяют процесс инструмента от harness/модели; неизвестные счётчики остаются null. Динамический обзор собственных временных файлов помечается non_atomic_live_inventory; исчезнувшие атомарные .tmp учитываются отдельно, прочие ошибки доступа не скрываются. Нехватка места не удаляет доказательства.

В каталоге0.13: case.analyze/show/coverage/events/evidence/compare, comparison.show, source.check, knowledge.search/card, os.collect/import, artifact.show. Операции чтения можно выполнять и существующими короткими CLI-командами. Новые анализы и сборы выполняй через сохранённый запрос. При осмотре источника сохраняется ограниченная выдача, не полный снимок внешнего файла; поиск знаний остаётся кандидатом, а не knowledge-use. RAC/PostgreSQL, ЖР, выгрузка/снимки исходников, APDEX, запись Investigation/профиля/черновика пока имеют отдельные прямые маршруты. Существующий source-export сохраняет свой план и защиту от повторного запуска. Общая оркестрация всего плана, CodeMode и MCP этим каталогом не объявляются готовыми.
