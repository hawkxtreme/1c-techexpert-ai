# Каталог и сохранённый запуск операции

Это средства текущего агента, а не требование к пользователю писать JSON. Сначала выбери проверку и согласованные источники/пределы из задачи, затем сам подготовь частный запрос. Сохранение GUI не вызывает эти операции. ИИ интерпретирует результат отдельно; `succeeded` не означает подтверждённую причину или полноту источника.

```powershell
python techexpert.py capabilities
python techexpert.py capabilities case.analyze
python techexpert.py --state-dir "D:/private/techexpert-state" operation-run "D:/private/sc01-request.json"
```

Каталог содержит исполняемые схемы аргументов и результата, источники, права, область, предел времени/результата и влияние. Дополнительные свойства, произвольные команды, исполняемый код и секреты не принимаются. Доступы остаются у текущего пользователя ОС; executor_id — заявленная метка harness, не проверенная учётная запись или новая выдача прав.

Пример запроса, который агент сохраняет до первого вызова:

```json
{
  "schema_version": 1,
  "operation_key": "sc01-first-import-unique-plan-id",
  "executor_id": "current-harness-session-id",
  "operation": "case.analyze",
  "arguments": {"manifest": "D:/private/incident/manifest.json"},
  "budget": {"timeout_seconds": 60, "max_result_bytes": 16777216}
}
```

max_result_bytes относится ко всему возвращаемому JSON в UTF8/LF, включая служебные поля и завершающий перевод строки. Первый ответ имеет replayed:false; повторное чтение — replayed:true. Если текущие предупреждения на повторе перестали помещаться, выдача имеет status:partial, execution_status прежнего запуска, data_omitted:true и truncated:true. Это усечение текущего представления, а не повторная обработка или изменение сохранённых фактов. Не запускай импорт/сбор заново для восстановления пропущенного текста.

Ключ обозначает один согласованный шаг. Создай и сохрани его перед запуском; после потери ответа используй тот же файл/ключ. Другой executor может прочитать этот запуск. Смена аргументов, бюджета или ожидаемой ревизии с тем же ключом даёт конфликт. Для действительно нового сбора нужен отдельный шаг и новый ключ в пределах уже разрешённого плана; не меняй ключ, чтобы обойти неизвестный исход старого запуска. Повтор не открывает оригиналы и не создаёт второй case/artifact. Числа и ссылки сохранённого результата проверяются по удержанным свидетельствам; порча не вызывает новый импорт. Текущий current_knowledge_review добавляется отдельно при чтении, исходная data и прежний файл не переписываются; прежняя data.knowledge_review относится к моменту того вычисления.

Необязательный context задаёт investigation_id и expected_revision. Перед стартом сверяются ревизия и хэш; запрос с устаревшей ревизией не запускается. Сбор сохраняет свой контекст, даже если в это время меняется профиль/расследование. Полученный case_id/artifact_id/comparison_id подключай к Investigation отдельным обычным update с актуальной ожидаемой ревизией, не переписывая чужие изменения.

```powershell
python techexpert.py operation-status RUN_ID
python techexpert.py operation-result RUN_ID
python techexpert.py operation-cancel RUN_ID --executor-id current-harness-session-id
python techexpert.py operation-reconcile RUN_ID
python techexpert.py kernel-call KERNEL_CALL_ID
```

Run_id — 64 шестнадцатеричных символа, отдельный от 32-символьных ID свидетельств. Состояния preparing/starting/running/stopping означают подготовку, записанный дочерний процесс, подтверждённый вход исполнителя и остановку. Запрос отмены хранится отдельно. Только stop_verified подтверждает локальную остановку; старый heartbeat сам по себе этого не доказывает. CLI возвращает JSON; журнал этапов хранится частно в operations/RUN_ID/journal.jsonl. Коды нового маршрута: 0 выполнено, 1 частичный/ожидающий/прерванный результат, 2 неверный вход, 3 ошибка исполнения, 130 отмена. Недостаточность данных для причины не является ошибкой исполнения инструмента.

Reconcile получает системную блокировку записи и проверяет реальные PID вместе с временем создания/эпохой, ОС и областью PID. Чужая ОС, другой Linux PID namespace или неизвестная область не позволяют подтвердить остановку. При живом или неизвестном владельце не забирает работу. Если процесс завершился и оставил целый запечатанный результат при тех же совместимых версиях правил, завершается только перенос в штатное частное хранилище; вычисление не повторяется. Полный первый payload запечатывается до переноса с хэшами плана/worker и размером прошедшей проверки выдачи. Если последний receipt не удалось записать, status/result и повтор ключа показывают incomplete_commit; после исправления доступа явный reconcile проверяет этот payload и завершает только запись/проверку готовых файлов без нового исполнителя. Исходный output.json при этом не растёт и не переписывается, а новые recovery-метаданные текущего view при необходимости усечены в пределах прежнего бюджета. Повреждённая подготовка не пересоздаётся; reconcile не обходит исходный отказ по лимиту. Прежняя ошибка остаётся в журнале и recovery_previous_reason, а не выдаётся за новую причину остановки. Без запечатанного результата сохраняется прерванное состояние. Повреждение, неизвестная группа процессов и неподдержанный профиль требуют разбора; не удаляй lock/state для обхода. В Linux смерть ведущего процесса не доказывает остановку группы; неполная видимость процессов остаётся неизвестной.

Штатная отмена локального ОС-сбора даёт короткую паузу на сохранение частичных отсчётов. Затем останавливается только собственное дерево. После аварии несохранённая память не восстанавливается; удержанные файлы не выдаются за готовый отчёт. Windows требует подтверждённую поддержку FileRenameInfoEx/POSIX semantics для частного состояния (проверено на местном NTFS), использует Job с kill-on-close и пределом памяти; Linux — отдельную сессию, ограничение адресного пространства и собственный watchdog исполнителя. При закрытии модели пределы не требуют её опроса. После обрыва SSH/WinRM подтверждается только местная часть; завершение удалённого процесса остаётся неизвестным, его штатный probe ограничен переданной длительностью.

Общие пределы исполнителя: результат до16MiB, собственные файлы до256MiB/1000членов, свободное место не ниже10GiB. Диск/вывод проверяются периодически, возможен выброс; нехватка места не удаляет доказательства. Динамический обзор .tmp помечен non_atomic_live_inventory; прочие ошибки доступа не скрываются. В управляемом CLI приём исходного JSON имеет10с. После приёма timeout_seconds запроса считается от общего начала вызова без сброса часов; отдельные чтения/отмена/reconcile имеют30с. Остановка/закрытие handles может добавить до5с. ОС-пресет300с/1с изменяем, максимум1800с.

Управляемый Windows Job ограничен1GiB для контроллера и локальных потомков, включая вложенные Jobs; измеряется committed memory. На Linux каждый процесс наследует предел адресного пространства до1GiB, меньший не поднимается; общий RSS/пик дерева неизвестен. kernel_call_id включён до первого полного byte-gate; kernel-call показывает отдельную квитанцию с фазами, хэшами и доступными счётчиками. Малый транспорт читает/передаёт чанки до64KiB без полного JSON decode, но setup/receipt/stream I/O не имеют отдельной жёсткой квоты ОС. Прямой внутренний Python engine, другие legacy-команды, модель/harness и удалённые узлы не получают эти гарантии автоматически. После обрыва контроллер и worker имеют собственные deadline/parent-lifetime watchdog; локальная остановка не подтверждает удалённую.

В каталоге 0.27: input.inspect, case.analyze/show/coverage/events/evidence/compare, comparison.show, source.check/compare, sample.describe, knowledge.search/card, os.collect/import, artifact.show/evidence, apdex.import, jr.import/events/record, source.snapshot/search/read, rac.observe, postgresql.observe и investigation.sources. Эти 27 диагностических операций доступны через управляемый CLI, [MCP STDIO](mcp.md) и code.execute; code.inspect читает сохранённую программу. Схемы каждого вызова возвращает capabilities. Агент готовит запрос и область источников; пользователю не требуется писать JSON. Повтор ключа проверяет прежние частные снимки без повторного сбора. Частичный APDEX/ЖР и недоступный RAC/PostgreSQL возвращают partial: успешное чтение сохранённого артефакта не устраняет ограничений его источника. Отмена текущего сбора отличается от чтения ранее отменённого. При осмотре ТЖ сохраняется ограниченная выдача, не полный снимок внешнего файла; поиск знаний остаётся кандидатом, а не knowledge-use. Прямые короткие команды сохраняются, но их гарантии уже управляемого маршрута. Выгрузка основной конфигурации, запись расследования/профиля/черновика и knowledge-use выполняются отдельно по собственным контрактам; source-export сохраняет прежнюю защиту от повторного запуска. [Навык программной обработки](../../code-mode-analysis/SKILL.md) задаёт ограниченную композицию API; общий исполнитель всех изменяющих действий плана пока отсутствует.

Квитанции вызовов сохраняются частно в kernel-calls отдельно от исходных отчётов. Windows Job peak означает committed bytes, Linux self ru_maxrss — RSS; эти числа не складывай и не сравнивай как один показатель. Недоступные память транспорта/модели и общий Linux peak остаются null. Повреждение квитанции отклоняется; потеря финальной квитанции вызова даёт incomplete_invocation_receipt и не удаляет операционный output.json. После неопределённого исхода используй прежний ключ/operation-result, не новый импорт. Журнал вызовов не является готовым обезличенным пакетом для публикации.

При kernel_receipt_commit_failed операция и её исходный response могут быть уже сохранены, а квитанция вызова — нет. Возвращается partial/incomplete_invocation_receipt с указателем на прежний ответ; при запрете записи доступен небольшой аварийный JSON через транспорт. Это не повод повторять импорт с новым ключом. kernel-call различает сохранённую фазу и фактическую идентичность процессов. Ошибка только advisory status cache не скрывает уже проверенную final receipt и сообщается отдельно в stderr/diagnostic.

## Просмотр входов и выбор файлов

`python techexpert.py capabilities input.inspect` возвращает схему inputs/limits. Например, arguments: `{"inputs":[{"path":"D:/logs/episode.zip","kind":"zip"}]}`. Допустимы также file и directory. Агент сохраняет запрос с ключом и выполняет `operation-run REQUEST.json`. Ответ — artifact_id и result.members с ID, относительными именами и размерами; это просмотр, без распаковки и анализа.

Для анализа агент создаёт обычный case-манифест с `sources[].path`, равными выбранным ID (`m1` и т.п.), и явными поддержанными форматами/профилями. В запросе case.analyze передаются `manifest` и `input_plan: artifact_id`. Новый изменившийся состав не принимается по старому просмотру. Повтор завершённого ключа проверяет прежние частные свидетельства без оригиналов. В CodeMode точные настройки просмотра задаются в scope.intakes, манифест — в scope.manifests, уже существующий план — в scope.artifacts; план, созданный разрешённым input.inspect, доступен в той же программе.

## Выбранные входы ЖР и измерений

После input.inspect существующие jr.import/os.import/apdex.import принимают парные input_plan и members. Схемы возвращает capabilities; CLI вызывает их через operation-run, MCP — через прежние инструменты. Новых диагностических API нет. path (ЖР) либо measurements (ОС/APDEX) указывает исходный корень плана, а не путь частной staging-копии; выбранные members должны принадлежать этому корню. ЖР — одна группа одного родителя, один1Cv8.lgf и1..31LGP, без одинаковых имён; ОС/APDEX — один файл. Импорт проверяет исходный состав и байты, собственный парсер формата и совпадение сохранённых байтов с выбранным снимком. Родительский каталог фиксируется точным хэшем до первого результата и проверяется при управляемом replay.

CodeMode требует scope.artifacts для существующего плана (либо получает его из разрешённого input.inspect), scope.journals с точным корнем/профилем ЖР либо scope.measurements с корнем измерений. Разные выборки одного плана можно импортировать отдельно, одинаковый набор members не повторяется от перестановки ID. Обычный импорт без плана сохраняет прежние правила и не получает новых полей по умолчанию. Исходники1С в архивах исключены.

## Изменение сохранённых источников

source.compare — отдельная конечная операция чтения, не эксперимент case.compare по скорости/корректности. before и after требуют kind(case|artifact), id и source_id. Размер каждого выбранного источника до16МиБ; полные хэши проверяются даже после первого отличия или ограничения фрейминга. Выход содержит зависимости по точным отчётам, квитанциям и контексту манифеста/запроса, совпавшие байты, наблюдаемую связь, отдельно подтверждённый повтор материала и предложение диапазона чтения. Родительский input_catalog и привязка члена проверяются до первой выдачи и при managed replay. Ключ операции сохраняется; повтор читает прежний результат, не обновляет исходники. Новых продуктов кроме управляемого результата не создаётся. Изменённые selection/период, профиль/контекст/фильтры, исходный бюджет разбора, параметры адаптера или версия производителя требуют полной повторной интерпретации текущего источника, даже если байты дублируют прежний вход.

Для CodeMode нужны оба выбранных ресурса в scope.cases/scope.artifacts; связанный сохранённый input_catalog является проверяемой зависимостью выбранного материала и не разрешает читать другие оригиналы. Новый reader_scope в явном tj-prefix-v1 — хэш наблюдаемого kernel namespace (Linux boot/mount/time; Windows boot entry+kernel BootTime), без файлов состояния или hostname-fallback. Недоступность означает unknown. Это не удостоверение физического узла, исходного узла журнала или ИБ. Старые снимки не получают новый scope задним числом. Порядок сопоставляется по ограниченным монотонным отметкам только внутри одного наблюдаемого домена; UTC и синхронизация источников остаются отдельными.

Пути сравниваются лексически без открытия, регистр имён Windows не сворачивается. changed ID при том же пути — наблюдение замены, не доказанная ротация; другой путь при том же ID также не устанавливает механизм перемещения. Совпавший префикс не исключает ABA/обрезку и повторное наращивание между снимками. input_duplicate=true допускается для того же сохранённого источника либо проверенной повторной выборки того же saved catalogue member; иначе unknown. Проверка не считает уникальные реальные события, не меняет cause/occurrence и не склеивает равные payload. suggested_after_range — только подсказка чтения, включая прежний хвост; завершение фрейма не означает принятое событие.

## Описание измеренной выборки

sample.describe принимает inputs[{kind:case|artifact,id}] и operation. Доступны известные метрики выполнения сохранённого случая и исходные строки сохранённого apdex-measurements-v1. APDEX target не становится нормой. Для case название операции — заявление вызывающего агента; для APDEX оно также служит точным фильтром строк. context может описывать platform_version, workload, launch_conditions, selection_basis; reported_normal_seconds сохраняется как user_reported_not_measured. Агент берёт эти сведения из разговора и материалов, не требует новой формы от пользователя.

Необязательное window{start,end} отбирает начала операций в[start,end), оставляя исходную длительность целиком; неизвестное начало при таком фильтре исключается явно. Период не берётся из created_at отчёта. Статистика показывает число известных/пропущенных значений, медиану, диапазон, MAD и IQR; процентили используют линейную интерполяцию между упорядоченными позициями(n-1)*p и сопровождаются n. Это номинальные описательные числа, не повышение точности источника или доказательство нормальности/независимости. Неудачные попытки исключаются из распределения завершённых длительностей с явным счётчиком; неизвестные остаются неизвестными. Медленные наблюдения не отбрасываются.

Пределы:16 ресурсов,64МиБ сохранённых исходных байтов суммарно,100000 просмотренных наблюдений, offset и limit(1..200) для выдачи. Каждая страница проверяет полные источники; сводка и selection_sha256 относятся ко всей выборке. Тот же выбранный ID нельзя добавить дважды. Повтор представления одного проверенного catalogue member не увеличивает выборку; равенство текста разных файлов не доказывает один эпизод. Для противоречащих интерпретаций одного материала сохраняются обе записи с исключением из агрегата.

В CodeMode нужны все inputs в scope.cases/artifacts. Родительский каталог является зависимостью целостности, а не разрешением читать другие артефакты. Управляемый результат фиксирует отчёты, квитанции, контекст и источники до первой выдачи; повтор ключа работает со снимками. Новый сбор не запускается, прежние оценки не меняются. Для SC01 case.compare дополнительно показывает распределения групп, сохраняя собственный протокол и критерии эффекта.
