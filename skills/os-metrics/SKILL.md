# Метрики ОС

Новый разрешённый сбор выполняй как `os.collect` через [operation-run](../techexpert/references/operations.md): сохрани частный запрос и ключ до старта, при перерыве продолжай тот же запуск. Ключ не меняется для обхода неизвестного исхода. Штатная локальная отмена сохраняет частичные отсчёты; остановка местного дерева не доказывает завершение удалённого probe. Прямой os-collect сохранён для совместимости и не имеет общей защиты ключом.

Для сохранённого наблюдения укажи в `observation_plan` выбранные ID источников и окно с часовым поясом. Вызови `os-observation REQUEST.json` или `techexpert_os_observation` в режиме `preview` с текущим `context`, выбранной базой и общими лимитами. Когда пользователь разрешил этот объём работы, сохрани тот же план в режиме `approve` с `proposal_sha256`. Передай возвращённый `approval_sha256` и `source_id` в поле `observation` у `os.collect`. Режим `status` показывает остаток времени, объёма и числа запусков, а также исход предыдущих проверок.

Прочитайте профиль и [методику дисков](../../knowledge/methods/os-disk.md). Покажите цель, узлы/роли, транспорт, период, длительность, шаг и предел объёма. Пресет нового плана — 300 с / 1 с; сохранённые значения имеют приоритет. Разрешённый план выполняйте без повторных вопросов.

`python techexpert.py os-plan --duration 300 --interval 1` только готовит параметры. `os-collect` явно запускает один сбор. Для SSH добавьте --transport ssh --host user@node, для WinRM — --transport winrm --host node. При необходимости SSH использует --identity-file и --known-hosts-file, сохраняя проверку ключа сервера. На удалённом узле нужен Python 3.10+; служба и доступ должны существовать заранее. WinRM использует текущую авторизацию Negotiate; службы/TrustedHosts/права не меняются.

Локальный результат и `os-import measurements.json` сохраняются как artifact_id. Первое измерение и недоступные счётчики могут быть unknown. Проверяйте scope, полноту и сбросы. При обрыве SSH/WinRM остановка удалённого процесса остаётся неизвестной. Штатное достижение лимита объёма даёт частичные измерения и явный результат завершения.

Команды запускайте из проверенного корня пакета; [общий контракт](../techexpert/references/local-cli.md) задаёт состояние и формат ошибок.

Для готового файла измерений в каталоге или ZIP используй input.inspect, затем os.import с парными input_plan/members. measurements — исходный корень просмотра, members содержит ровно один выбранный JSON штатного формата. Это импорт существующих измерений, без запуска сборщика. В CodeMode нужны scope.measurements для корня и доступ к артефакту плана. Разные файлы одного архива можно импортировать по одному; повтор одной и той же выборки требует отдельного разрешённого действия. Узел, роль, фактические интервалы, пробелы и неизвестные счётчики берутся из данных. Сохранённый результат читается без оригиналов; повреждение снимка или каталога блокирует управляемый повтор.

Для проверки диска за период расследования прикрепи сохранённые измерения и используй `os-window`. Сопоставь очередь с задержками, IOPS и байтами в секунду по каждому объекту. Проверь, что устройство относится к нужному узлу и базе, а записанные времена сопоставимы. [Выборка по окну](../techexpert/references/mcp.md#выдача-сохранённых-данных-модели)

При проверке локального диска файловой базы передай `map_file_storage: true` в `preview` и `approve` наблюдения. Путь берётся из выбранной базы в сохранённом профиле. Сборщик наблюдает устройство до и после сбора. В `os-window` сначала идут однозначно сопоставленные экземпляры счётчиков. Для разового локального сбора можно передать `--storage-path` или `storage_path` с явно выбранным путём. Учитывай область счётчиков и основание `storage_binding.origin` при выводе о причине.

Если нужны счётчики процесса, добавь `process` с `source_id` локального источника в тот же план. Для файловой базы Windows агент ищет единственный клиент, открывший её файл. Если процесс уже известен, укажи также `pid`. Проверь выбор в `preview`. План закрепляет время создания процесса, поэтому повторное использование PID не меняет цель. Прочитай `os-process-window` по тому же интервалу и проверь число пригодных пар измерений. Windows учитывает все вводы-выводы процесса, Linux показывает учёт чтения и записи хранилища ядром. Оба показателя относятся ко всему процессу. Для вывода о конкретном диске, базе или задании нужны дополнительные доказательства. [Windows](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters) · [Linux](https://docs.kernel.org/filesystems/proc.html#proc-pid-io-display-the-io-accounting-fields)
