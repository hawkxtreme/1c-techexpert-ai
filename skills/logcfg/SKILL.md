# Настройка технологического журнала

Используй, когда не хватает событий или периода для расследования. Сначала используй доступные журналы: новый сбор не восстанавливает прошлый эпизод. Настройка относится к выбранному процессу и узлу; каталог ТЖ и путь logcfg.xml задаются независимо от каталога ИБ. Для файловой базы выбирай клиент/терминал/веб по месту выполнения, обязательного rphost нет.

## Подготовить файл

Исполняемые API: `logcfg.prepare` и `logcfg.rollback_plan`, через MCP либо [управляемый CLI](../techexpert/references/operations.md). Команды/JSON готовит агент. Применение на узле в этих API отсутствует.

Для существующего ТЖ прочитай указанную копию через `source.check` с `profile_journal.logcfg_file`. Если путь неизвестен и выбран локальный клиент 1С для файловой базы Windows, передай его PID через `profile_journal.logcfg_process_pid`. Агент проверит версию и расположения по порядку поиска. Для выбранного каталога ТЖ видно правило, ротацию, хранение и распознанные фильтры. [Чтение ТЖ и применение профиля разбора](../techexpert/references/mcp.md#первичный-приём-тж-и-жр)

Возьми известные сведения из профиля и разговора. Если расположение конфигурации неизвестно, помоги администратору определить активный conf для выбранного процесса и учётной записи по [руководству 8.3.27](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/). Типовые каталоги установки и пользовательских настроек — кандидаты, не доказательство найденного файла. Отсутствие доступа не означает отсутствие файла.

В `logcfg.prepare` передай:

- `current_file`: явно предоставленная локальная стабильная копия текущего XML, до 1 МиБ, UTF-8. При подтверждённом администратором отсутствии файла вместо неё `current_absent:true`.
- `node`, `os:windows|linux`, `mode:file|server`, `process:client|terminal|web|rphost|rmngr|ragent`, `platform_version:8.3.27.1989`.
- Подтверждённые абсолютные `config_path` с именем logcfg.xml и отдельный `log_location`. Эти пути на узле не проверяются данным действием.
- `purpose`, явный список `events` из схемы API. Выбирай события под гипотезу; обязательного списка для всех проблем нет.
- `history_hours` (по умолчанию 1), `duration_seconds` (300), `max_bytes` (16 МиБ). Период подбирай под эпизод отдельно от короткого OS-сбора.

`ready` означает отдельный проект: добавлен собственный помеченный блок, существующие правила/комментарии/дампы сохранены. Ограниченный профиль text/plain, ротация по размеру. Уже занятый каталог даёт `needs_review`: разбери текущие правила или выбери отдельный каталог. Ошибочный XML, неизвестный корень/кодировка и превышение сложности дают причину без готового файла.

Этот генератор фильтрует только имена событий. Роль процесса и база в контексте не становятся фильтрами XML: будут записываться совпадающие события всех процессов, использующих данный конфигурационный файл. До применения администратор проверяет эту область и влияние общих настроек; узкую привязку к процессу/ИБ данный профиль не обещает.

Покажи `logcfg.xml`, `change.diff` и исходную копию из `sources`. `artifact.evidence` по source_id проверяет полные байты и возвращает абсолютный частный путь и ограниченный текст. Файлы находятся в частном состоянии вне репозитория. XML и контекст событий могут содержать чувствительные сведения.

## Проверить применение

Передай администратору конкретный проект и план из результата. Перед применением сравнить текущий файл с SHA256 исходной копии либо повторно подтвердить отсутствие: расхождение требует нового проекта. Затем резервная копия, применение в подтверждённый conf и проверка прав реальной учётной записи процесса читать конфигурацию и писать в каталог ТЖ. На Linux нужен доступ UID процесса ко всем родительским каталогам, на Windows — доступ реального пользователя/службы.

XML и статическая проверка добавленного блока не подтверждают принятие платформой. Дождаться перечитывания настроек, выполнить небольшой разрешённый тест и проверить новые события, время/узел, рост каталога и нагрузку. Если событие не пришло, сбор остаётся неподтверждённым: проверить путь, процесс, права и фильтры. Нагрузка заранее неизвестна; сначала измеряется на представительном коротком окне.

`history` — хранение в часах. Этот конечный профиль без архиватора требует хранения не короче запланированного периода: для суток укажи минимум 24 часа, что само по себе не подтверждает полноту. Длительность и предел байтов из плана **не исполняются XML**: администратор или отдельно разрешённый контроллер останавливает сбор по первому достигнутому условию. Для периодической проблемы подготовь источники, сохрани ожидание в том же чате и продолжи после сообщения о произошедшем эпизоде. Подготовка не запускает суточный сборщик.

## Вернуть настройки

Получи свежую локальную копию текущего файла. Вызови `logcfg.rollback_plan` с `proposal_id` исходного проекта и `current_file` этой копии. Точное совпадение возвращает исходные байты; исходное отсутствие — отдельный план удаления. Более поздние посторонние правки сохраняются удалением только неизменённого собственного блока. Изменённые/дублированные/пропавшие маркеры требуют разбора. Перед исполнением сравнить SHA256 текущей копии; сам план ничего не применяет и собранные журналы не удаляет.

Для чтения нового ТЖ выбери фактический [профиль источника](../techexpert/references/local-cli.md), проверь реальные заголовки, версию и часовое смещение. Plain/размерная ротация не доказывает ISO-время или полноту. Единицы длительности записи и XML-фильтра различаются; этот генератор фильтр duration не создаёт. Затем продолжи [расследование](../investigate/SKILL.md) по исходной проблеме.
