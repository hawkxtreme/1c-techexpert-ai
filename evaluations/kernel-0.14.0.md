# Управляемый контроллер SC-01, локальный профиль0.14.0

Управляемые operation-run/status/result/cancel/reconcile теперь выполняют приём исходного запроса, выборку сохранённых данных, проверку и финальную запись в отдельном процессе. Текущий harness по-прежнему интерпретирует факты сам; ядро не запускает отдельную модель. Каталог содержит прежние13 операций и фиксированные команды управления; произвольного исполняемого кода в запросе нет. Прямые legacy-команды и внутренние Python-функции не получают этот контракт автоматически.

| Область | Подтверждаемый предел/измерение | Ограничение |
| --- | --- | --- |
| Приём исходного JSON | До128KiB,10с в контроллере | Часы общего вызова не сбрасываются после приёма |
| Выполнение/повтор/commit | timeout_seconds запроса; команды чтения/отмены/reconcile30с | Ограниченная уборка/закрытие handles может добавить до5с |
| Windows controller tree | Job committed memory до1GiB, CPU и Job peak, локальные вложенные Jobs | Не RSS, не память harness и не удалённого узла |
| Linux процессы | Унаследованный RLIMIT_AS до1GiB на процесс; меньший сохраняется | Общая память дерева не ограничена/не измерена этим механизмом; cgroup delegation не предполагается |
| Linux счётчики | self CPU/RSS и отдельно дождённые потомки | CHILDREN ru_maxrss — крупнейший ребёнок, не пик одновременного дерева |
| Файлы вызова | До64MiB/1000членов, вывод диагностики64KiB; запас10GiB | Периодический контроль допускает выброс, атомарной дисковой квоты нет |
| Ответ | Прежний max_result_bytes, включая kernel_call_id и LF | Изменившийся текущий view может быть явно усечён |
| Транспорт/внешний клиент | Малые метаданные и чанки до64KiB без полного JSON decode | Setup/receipt/stream I/O не имеют отдельной квоты ОС; backpressure клиента и ресурсы модели не контролируются |

Каждый вызов имеет отдельный kernel_call_id и частную квитанцию. В неё входят фактические длительности, Python/ОС/архитектура/число логических CPU, доступные процессные счётчики, пределы, hashes ответа и область наблюдения. Неизвестные токены, память harness, память транспорта и общий Linux peak остаются null. Это ещё не полный протокол оборудования/холодных и повторных серий всего расследования REQ-78.

Служебная ссылка на вызов включается до первоначальной проверки размера и переноса продукта. Позднее добавление счётчиков не увеличивает сохранённый отчёт: они читаются отдельно через kernel-call. Повтор ключа остаётся чтением прежней операции. Подготовленный payload0.13 и границы queue/execution/observed calls/cause сохраняются. Ошибка памяти во время исполнения или сериализации отделяется от необъяснённого завершения процесса; последний случай не объявляется доказанным OOM.

Проверки включают остановку зависания до приёма оригинала, зависание replay и финального переноса, восстановление запечатанной работы без повторного импорта, отказ при превышении полного wire-бюджета и порче счётчиков/ответа, незавершённую квитанцию, отмену и наследование меньшего лимита. На Windows контролируемая авария сразу после CreateProcess выявила окно до AssignProcessToJobObject; PROC_THREAD_ATTRIBUTE_JOB_LIST закрывает его при создании. На Linux cleanup держит ведущий PID недождённым через waitid/WNOWAIT до остановки собственной группы. Нет сигнала по PID, найденному в старом состоянии; чтение чужой операции не делает её сборщик собственностью текущего вызова.

Контроллер и worker имеют независимые deadline/parent-lifetime watchdog. Неизвестная идентичность или видимость процессов не превращаются в ноль использования; отмена и остановка различаются. Завершение локального SSH/WinRM клиента не устанавливает завершение удалённого probe. Полный план с суммарным бюджетом повторов, единый исполнитель остальных адаптеров, миграции/retention и обезличенный support bundle остаются отдельной незавершённой работой. Наличие resource boundary не подтверждает качество модельного диагноза или все требования ТЗ.

Семантика сверена с первичными описаниями: [вложенные Windows Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs), [атрибут Job list при создании](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [Python3.12 resource](https://docs.python.org/3.12/library/resource.html), [Linux getrusage](https://man7.org/linux/man-pages/man2/getrusage.2.html), [cgroup-v2 delegation](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html). Полные исходные статьи/книги не включены. Фактический local/portable результат фиксируется внешней квитанцией конкретного SHA; облачный CI и серверный SC-01 с лицензией этим документом не объявляются выполненными.

Независимый ревью первого кандидата подтвердил два P2, несмотря на зелёный общий прогон: actual call-receipt write fault сохранял running после смерти владельца, а два Windows ожидания давали10,02с в согласованной синтетической модели неизвестной остановки. Это не измерение реального зависшего драйвера. Регрессии воспроизводят именно отказ записи, включая отказ записать сообщение об этом и реальный завершённый owner. Исправление оставляет исходный response/operation output неизменными, возвращает partial либо малый inline frame при запрете записи, различает завершённую проверенную квитанцию и сбой advisory status cache. При чтении без final receipt показываются реальные наблюдения PID/lifetime, а не прежняя метка running. Windows settle и finally handle-wait расходуют один общий cleanup deadline; неизвестное дерево остаётся неизвестным.
