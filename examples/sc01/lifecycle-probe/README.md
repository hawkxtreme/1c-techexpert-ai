# Контроль жизненного цикла фонового задания

Это добровольно запускаемая **тестовая конфигурация для новой пустой файловой базы**.
Не импортируйте её в рабочую базу и не переносите модули в прикладную конфигурацию.
Два последовательных фоновых задания используют один ключ: первое завершается,
второе после двухсекундной паузы вызывает контролируемую ошибку. Проверяются
фактические UUID, состояния и связь с ТЖ. Задержка «45 минут вместо пяти» здесь
не воспроизводится; короткий тест не доказывает причину медленной загрузки.

В `config/` находятся собственные исходники BSL и XML минимальной конфигурации.
Бинарников платформы, базы и собранных журналов в примере нет. Формат снимков:
`schema=1`, `artifact_profile=sc01-platform-background-job-v1`,
`instrumentation_version=4`, `origin=controlled_real_background_job`.

## Подготовка и запуск

1. Подготовьте отдельную копию установленной платформы и новую пустую файловую
   базу в выделенном каталоге лаборатории **вне репозитория**. Не используйте
   рабочие базы, общие настройки `logcfg.xml` или пользовательские конфиги.
   Для физической копии `bin` сначала проверьте reparse points/ссылки; не применяйте
   hardlinks или junctions и не переносите существующий `conf` с частными настройками.
   Платформа и законное право её запуска должны уже иметься; пример ничего не
   устанавливает и не активирует. Сохраните не менее 10 GiB свободного места.
2. Создайте отдельные пустые каталоги для снимков и ТЖ. В
   `logcfg.example.xml` замените `ABSOLUTE_TJ_CAPTURE_DIRECTORY` абсолютным путём
   каталога ТЖ. Поместите этот файл как `conf/logcfg.xml` только в изолированную
   копию платформы. Шаблон сам по себе не ограничивает общий размер журнала.
3. Из harness запустите следующие операции последовательно, используя полный
   путь **изолированного** `1cv8.exe`. Ниже приведены массивы аргументов для
   ограниченного launcher, а не готовый shell-скрипт. Все `<...>` нужно заменить.
   Для первого прогона используйте пути лаборатории без пробелов; это исключает
   неоднозначность вложенных кавычек строки `File=...;`.

   ```text
   ["CREATEINFOBASE", "File=<new-test-ib>;", "/DisableStartupDialogs", "/Out", "<create.out>", "/DumpResult", "<create.result>"]
   ["DESIGNER", "/F", "<new-test-ib>", "/LoadConfigFromFiles", "<absolute-probe-config>", "/DisableStartupDialogs", "/Out", "<load.out>", "/DumpResult", "<load.result>"]
   ["DESIGNER", "/F", "<new-test-ib>", "/UpdateDBCfg", "/DisableStartupDialogs", "/Out", "<update.out>", "/DumpResult", "<update.result>"]
   ["DESIGNER", "/F", "<new-test-ib>", "/CheckConfig", "-Server", "-ThinClient", "-ExternalConnection", "/DisableStartupDialogs", "/Out", "<check.out>", "/DumpResult", "<check.result>"]
   ["ENTERPRISE", "/F", "<new-test-ib>", "/C", "<absolute-empty-snapshot-directory>", "/DisableStartupDialogs", "/DisableStartupMessages", "/DisableSplash", "/Out", "<run.out>"]
   ```

   `ПараметрЗапуска` читает `/C` в клиентском модуле и передаёт путь серверному
   коду. Путь обязателен, должен быть абсолютным локальным путём на узле процесса
   1С; каталог должен уже существовать и быть пустым. Каталога по умолчанию нет.
   Проверки выполняются до запуска заданий; первая запись batch также проверяет
   возможность записи. Клиент и worker рассчитаны на один узел файловой базы.
4. Launcher должен запускать процесс скрыто, записать его точный PID, время старта,
   версию платформы, аргументы, UTC и смещение часов узла, хэши исходников/ТЖ;
   ограничить каждую операцию 30 секундами, весь ТЖ прогона — 16 MiB и следить за
   свободным местом. При превышении предела останавливайте только собственный
   запущенный процесс; сохраняйте неполный результат. Такой launcher сюда не
   включён. Ожидание каждого задания внутри конфигурации ограничено 15 секундами,
   но это **не** замена внешнего ограничения процесса.
5. Для создания/импорта/обновления/проверки требуйте код выхода 0, значение
   `DumpResult` 0 и отсутствие ошибок проверки. Для выполнения одного exit code
   недостаточно: нужен завершённый `batch-*.json` с `expected_cases_passed=true`,
   двумя разными UUID и одинаковым фактическим ключом. Ошибка параметра `/C`
   выводится клиентом; без итогового batch прогон не считается успешным.

Не добавляйте базу в пользовательский список (`/AddToList` не нужен). Перед новым
прогоном выберите новый пустой каталог снимков. Конфигурация ничего не удаляет.
Результаты содержат имя компьютера и путь выбранной тестовой базы: храните их
локально вне Git; публикуйте только проверенную обезличенную выборку.

## Что означают результаты

| Артефакт | Значение |
| --- | --- |
| `batch-*.json` | Общий ключ, два результата, проверка различия UUID и ожидаемых исходов. |
| `controller-*.json` | Наблюдения до/после `Выполнить`, затем обновлённое через `НайтиПоУникальномуИдентификатору` состояние и платформенные `Начало`/`Конец`. |
| `worker-enter-*.json` | UUID фактического текущего задания, номер сеанса/соединения; вход в тело callback. |
| `worker-exit-*.json` | Точка перед возвратом успешного callback; ещё не платформенный конец задания. |
| `worker-raise-*.json` | Точка непосредственно перед намеренным исключением; состояние `failed` подтверждает controller. |
| ТЖ `SESN` и `SDBL` | Реальные сеансы и запросы-маркеры `SC01LIFECYCLE:<phase>:<nonce>:<job_uuid>`; их наличие и связь нужно проверить в захвате. |

Ключ задания не идентифицирует запуск. `submit_requested` и `execute_returned`
не дают точного времени постановки в очередь. Интервал `SESN` описывает сеанс,
отдельный `CALL`/`SCALL` или маркер — вызов/точку тела, а не всё задание.
`session_id` — номер, не UUID; сопоставляйте его с `SESN.Nmb` только в пределах
известных базы, узла, процесса и его времени жизни. `SESN.ID` берётся из ТЖ:
свойство UUID у объекта `СеансИнформационнойБазы` здесь не выдумывается.

`observed_utc_ms` — UTC-миллисекунды от **0001-01-01**, не Unix epoch.
`observed_utc_seconds` выводится из того же замера и содержит явный `Z`;
два вызова часов на границе секунды не смешиваются. Платформенные даты `Начало`/`Конец`
сохранены отдельно с точностью до секунды без приписанного часового пояса.
Для ТЖ смещение задаёт оператор по контексту захвата. Например, явное
`timestamp_offset: "+03:00"` означает, что `2026-01-01T12:00:00` соответствует
`2026-01-01T09:00:00Z`; **+03:00 — пример, не значение по умолчанию и не
автоматическое определение**. Сверяйте его с независимыми UTC-наблюдениями.

## Проверка и источники

Переносимый вариант с `/C` (версия инструментации 4) реально прошёл импорт,
обновление, проверку конфигурации и выполнение на Windows / 1С **8.3.27.1989**.
Проверка конфигурации сообщила об отсутствии ошибок. Итоговый batch подтвердил
успешное и ошибочное задания с разными UUID при одном ключе. Процесс завершился
самостоятельно за 6,358 с; собрано 191 562 байта ТЖ. Хэши и результаты трёх
серий сохранены в [verification.json](verification.json): шесть отдельных заданий
прошли анализ через CLI, продолжение случая, проверку свидетельств и пагинацию.
Успешные задания связали по четыре записи тела; у аварийных без exit-маркера
сохранились платформенные границы при неизвестном участке тела. Межчасовые
расхождения явно отмечены, синхронизация не объявлена подтверждённой.

На версии инструментации 3 отдельно проверены отсутствующий, относительный,
несуществующий и непустой `/C`: ожидался конкретный отказ, фоновое задание
не начиналось, прежние снимки сохранены. Эти проверки пути в версии 4 не менялись.
Linux, клиент-серверный вариант и другие версии платформы не проверялись.

Синтаксис `/C`, импорта и проверки описан в
[официальном руководстве администратора 8.3.27](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/).
API `ПараметрЗапуска`, `ПолучитьРазделительПути`, `ФоновыеЗадания`,
`СеансИнформационнойБазы` и состояния задания сверены со штатной справкой
`shcntx_ru.hbk` этой версии. Встроенные паузы и исключение служат только
управляемому тесту; снимки не заменяют независимый ТЖ и receipt запуска.
