# Вход

Свободное описание симптома, ключевые слова/пользователь, период, идентификатор базы (если известен).

# Алгоритм

1. Найти конкретный запуск фонового задания по прикладной истории, ЖР и доступным идентификаторам; не выводить имя метода из ключевых слов без проверки.
2. Разделить время ожидания запуска и фактическую длительность выполнения.
3. Сравнить с сопоставимыми успешными запусками, нормализуя по объёму обработанных данных, если он известен.
4. В ТЖ восстановить корреляцию по узлу, процессу, сеансу и соединению. Сверить `CALL`, `SCALL`, события DB*, `TLOCK`, `TTIMEOUT`, `TDEADLOCK`, `EXCP` (если записывались).
5. Проверить SQL Server/PostgreSQL в read-only режиме. Учесть, что текущие DMV/pg_stat_activity не восстанавливают прошедший инцидент.
6. Классифицировать гипотезы: вырос объём, SQL, блокировки, внешнее API, повторные попытки, очередь запуска, ресурсы сервера.
7. Найти экспертные кейсы по фактическим признакам, но не считать совпадение подтверждением причины.
8. Сформировать отчёт: факты, ссылки на оригинальные свидетельства, уверенность, недостающие источники, безопасные следующие шаги.

# Правила

- Не суммировать перекрывающиеся длительности ТЖ без учёта иерархии вызовов.
- Не выполнять на продуктиве изменяющие данные команды или изменение logcfg.xml без отдельного разрешения.
- Не приписывать событие конкретному заданию только по близости времени.
